# Decisiones de diseño del backend — REDA (Programación 3)

| # | Decisión | Por qué | Alternativa descartada |
|---|---|---|---|
| P01 | Java 17 + Spring Boot 3.5 + Maven | Java 17 es la versión LTS instalada en el equipo; Spring Boot da inyección de dependencias, web, seguridad y JPA integrados | Java EE "a mano"; Spring Boot 4 (más reciente, menos material de referencia) |
| P02 | Arquitectura en capas `controller / service / model / repository` + `dto / exception / security / config` | Tema del curso; cada capa con un motivo de cambio | MVC con lógica en controladores |
| P03 | Nombres del dominio en **español** (`Reporte`, `cambiarEstado`), sufijos técnicos de Spring en inglés (`Controller`, `Service`, `Repository`) **(supuesto)** | Coincide con las tablas y el diccionario de datos; los sufijos son la convención del framework | Todo en inglés (rompe la correspondencia con la base) |
| P04 | JPA para el CRUD + **SQL explícito con JdbcTemplate** para el buscador de antecedentes y el mapa | Las consultas importantes del curso de BD se ven tal cual, parametrizadas | Todo con JPQL |
| P05 | `ddl-auto=validate`: Hibernate **nunca** crea tablas | El esquema lo dan las migraciones de `base-de-datos/`; `validate` detiene el arranque si Java y SQL no coinciden | `update` (Hibernate modificaría el esquema a escondidas) |
| P06 | Entidades sin setters; fábricas y métodos de negocio | Encapsulamiento: el estado solo cambia por operaciones válidas | Entidades "anémicas" con getters/setters |
| P07 | Validación en tres niveles: DTO (Bean Validation), dominio, base | Cada nivel atrapa lo suyo; la base es la última barrera | Validar solo en el frontend o solo en la base |
| P08 | Excepciones propias no verificadas con `CategoriaError` + un manejador global | Formato de error único; abierto a nuevas excepciones (ver auditoría SOLID, O1) | `try/catch` en cada controlador |
| P09 | JWT sin sesión en el servidor; secreto obligatorio por variable de entorno, validado al arrancar | La API no guarda estado; ningún secreto en el repositorio | Sesiones con cookie (requieren CSRF) |
| P10 | Contraseñas con BCrypt (costo 10); el registro público solo crea CIUDADANOS | Las cuentas con privilegios no se pueden autocrear | — |
| P11 | En un cambio de estado se usa `flush()`, no `save()` | **Error real encontrado en las pruebas:** `save()` sobre una entidad ya gestionada hace `merge`, que no propagaba la inserción del historial (fallaba con `id_reporte` nulo). La entidad ya está gestionada; `flush()` basta | `save()` + `CascadeType.MERGE` |
| P12 | Los reportes **rechazados** no cuentan como antecedentes | Detectado al probar el flujo de la demo; misma regla en la base (ver `base-de-datos/documentacion/decisiones.md`, D18) | — |
| P13 | Pruebas de integración contra PostgreSQL real, con `@Transactional` para deshacer los cambios | El equipo no tiene Docker (Testcontainers); H2 no soporta las vistas ni el SQL de PostgreSQL | H2 en memoria |
| P14 | El mapa público lee una **vista** de la base que ya oculta los datos personales | La privacidad no depende de que el código Java "se acuerde" de ocultar campos | Filtrar campos en Java |

| P15 | Interfaz **web responsiva** (HTML + CSS + JavaScript con módulos, sin framework) servida por el mismo Spring Boot | Una sola URL y un solo comando para la demo; funciona en PC y celular; la API REST queda lista para una app móvil nativa después. Angular agregaría una cadena de compilación que hoy no aporta | Angular; app de escritorio (JavaFX) |
| P16 | Mapa con **Leaflet 1.9.4** + **leaflet.heat 0.2.0** y teselas de **OpenStreetMap** oscurecidas con CSS | Gratis y sin clave. Los mapas base de CARTO empezaron a exigir API key (se vio la marca de agua al probar). La política de uso de OSM admite el tráfico de una demo; en producción se usa un servidor de teselas propio | CARTO, Mapbox, Google Maps (requieren clave/pago) |
| P17 | Los reportes se **agrupan en el backend** (radio 80 m, `AgrupadorPuntos`) y no con un plugin del navegador | La agrupación es regla del negocio ("punto de alta frecuencia"): queda probada y es la misma para web y móvil | Leaflet.markercluster (agrupa por píxeles según el zoom, no por metros) |
| P18 | Colores de situación: azul `#3987e5` (con abogado), naranja `#d95926` (abierto), verde agua `#199e70` (cerrado) | Paleta categórica validada con script para daltonismo sobre fondo oscuro (todas las parejas pasan); siempre con texto al lado | Morado/naranja/verde elegidos a ojo |
| P19 | Fotos privadas: se piden con el token y se muestran como `blob:` locales; respuesta con `Cache-Control: no-store` | Un `<img src>` no puede enviar el token; `no-store` evita copias en cachés compartidas | URL firmada temporal (más compleja) |
| P20 | El formato de la foto se valida por sus **bytes** y el permiso se revisa **antes** que el hash | Detectado al probar: revisar el hash primero le revelaba a un tercero que esa foto existía | Confiar en la extensión o el Content-Type |
| P21 | Fotos de la semilla sin archivo → imagen SVG generada que dice "foto de ejemplo · datos simulados" | La demo no muestra imágenes rotas y nunca hace pasar una imagen por una foto real | Fotos de internet (derechos, engaño) |
| P22 | Spring Security mantiene `X-Frame-Options: DENY` | Protege contra clickjacking; se notó al intentar incrustar la página en un iframe de prueba | Relajarlo para facilitar pruebas |

| P23 | **Todo exige sesión** salvo crear cuenta, entrar, recuperar contraseña y las páginas legales (decisión del grupo) | Los datos del mapa son de la comunidad registrada; la página de acceso explica el proyecto | Mapa público |
| P24 | Interfaz como **SPA con rutas `#/`** y un módulo por vista (`js/vistas/*.js`); el menú cambia según el rol | Sin configurar el servidor; cada vista es un archivo pequeño con una responsabilidad. El backend vuelve a verificar cada permiso: la interfaz no protege datos, solo oculta opciones | Un solo archivo JS |
| P25 | Registro de abogados **pendiente de verificación**; un administrador activa la cuenta | Evita que cualquiera se haga pasar por abogado y vea casos | Activación automática |
| P26 | Límite de **8 intentos cada 15 min** por correo (inicio de sesión, recuperación, cambio de contraseña) con respuesta 429 | Frena fuerza bruta. En memoria; con varios servidores iría a Redis | Sin límite |
| P27 | El correo de recuperación se escribe en la consola (`CorreoConsola`) detrás de la interfaz `EnvioCorreo` | No hay servidor de correo en el entorno; en producción se agrega una implementación SMTP sin tocar los servicios (DIP) | Integrar un proveedor ya |
| P28 | La respuesta de "recuperar contraseña" es **igual exista o no el correo** | No revela quién tiene cuenta (enumeración de usuarios) | Decir "ese correo no existe" |
| P29 | Calificaciones: el comentario se muestra **sin el nombre** del cliente ("Cliente en Centro · mayo de 2026") | Da contexto sin exponer a la persona | Mostrar el nombre |
| P30 | Estrellas: se dibujan redondeando hacia abajo en el medio punto (4,5 → 4 estrellas) y siempre con el número al lado | No exagerar la reputación; la cifra no depende solo del dibujo (accesibilidad) | Redondeo normal |
| P33 | El perfil público del abogado (foto, especialidad, presentación) solo se edita si está **verificado**: `Abogado.verificarPuedeEditarPerfil()` (Experto) | Nadie se presenta ante un ciudadano como abogado sin que REDA haya revisado su tarjeta. La insignia «✓ Abogado verificado» sale de `abogados.activo`, nunca de un dato que el abogado escriba | Permitir el perfil y ocultarlo |
| P34 | Quién ve una foto de perfil lo decide `Usuario.fotoVisiblePara`: el dueño y el personal siempre; la de un abogado verificado, cualquier usuario con sesión; la de un ciudadano, nadie más | La foto del ciudadano es un dato personal sin utilidad para los demás (minimización, Ley 1581). La foto se sirve con sesión y caché privada versionada (`?v=`) | Foto pública para todos |
| P35 | `FotoPerfilService` separado de `PerfilService` y de `EvidenciaService`, reutilizando `FormatoImagen` y `AlmacenamientoArchivos` (con carpeta `perfiles/`) | Alta cohesión y DIP. El archivo viejo se borra **después** del commit, para que la base nunca apunte a un archivo inexistente | Borrar antes de confirmar |
| P32 | El barrio se **sugiere** a partir del punto marcado (`GET /api/catalogos/zonas/sugerida`); la regla vive en `Zona` (Experto) | La zona conoce su ubicación, así que sabe a qué distancia queda un punto. Solo se sugiere si un barrio queda a ≤ 600 m (`reda.zonas.radio-sugerencia-metros`); si el ciudadano eligió a mano, no se le cambia | Calcularlo en JavaScript; obligar el barrio por distancia |
| P36 | **Menú lateral por rol** agrupado por tareas y una página **Inicio** por rol (cifras, «Requiere tu atención», accesos directos y «Cómo funciona»); en celular el menú es un cajón que se abre con ☰ | El usuario entra y ve de inmediato qué puede hacer y qué tiene pendiente, sin tener que descubrir el mapa. Inicio reutiliza los endpoints existentes (no se creó un endpoint de dashboard) | Barra superior con enlaces sobre el mapa (versión anterior) |
| P31 | Pruebas de interfaz con Edge controlado por CDP (`--remote-debugging-port`), emulando celular de 390 px | Edge sin ventana impone un ancho mínimo que impedía probar el celular; con CDP se emula el dispositivo y se inicia sesión de cada rol | Revisar a mano |
